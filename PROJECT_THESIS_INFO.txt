2. ABSTRACT (DRAFT — ADAPT FREELY)
--------------------------------------------------------------------------------
"Legal, administrative and business documents in India are written in more
than twenty languages, yet most document-AI tooling assumes English input.
This project presents MNER, a full-stack system that accepts documents
(PDF, DOCX, TXT, JPG/PNG) in 20+ languages — including Hindi, Tamil,
Kannada, Telugu, Malayalam, Bengali, Marathi and Gujarati — translates them
to English through a cascaded provider pipeline (cloud LLM, local LLM,
offline neural MT, web MT with verification), extracts named entities
(persons, organizations, locations, dates, amounts and more) using spaCy
plus legal-pattern correction, and answers natural-language questions
grounded in retrieved source clauses with citations. Long-running analysis
runs as asynchronous background jobs with live staged progress; all
processing can run fully offline via a local Ollama model, and uploaded
files are deleted after extraction (zero-retention privacy). The system
demonstrates that a hybrid of small local models, classical NLP and
cascaded translation can deliver usable multilingual document intelligence
on commodity CPU hardware."

3. PROBLEM STATEMENT & MOTIVATION
--------------------------------------------------------------------------------
- Indian users deal with contracts, government records and business papers
  in many scripts (Devanagari, Tamil, Kannada, Telugu, Malayalam, Bengali…).
- Mainstream NER models (e.g. spaCy en_core_web_sm) are English-only; there
  are no production-grade NER models for most Indian languages.
- Cloud translation APIs cost money, need internet, and leak private
  documents; free web endpoints rate-limit aggressively.
- Small local LLMs (4B class) can reason over documents but are slow on CPU
  (~6 tokens/sec measured) and ramble unless carefully constrained.
- Users need answers they can TRUST: every extracted fact must cite the
  source clause it came from (grounding), not hallucinated text.
- Therefore: build a pipeline that (a) normalizes any supported language
  to English through redundant providers, (b) extracts entities with
  classical + neural methods, (c) answers questions strictly from retrieved
  passages, and (d) stays responsive via async jobs even when backends
  take minutes.

4. OBJECTIVES
--------------------------------------------------------------------------------
O1. Accept PDF / DOCX / TXT / JPG / PNG / BMP / WEBP uploads (max 16 MB),
    including scanned PDFs and photos via OCR.
O2. Auto-detect document language (langdetect + dominant-script override at
    >8% non-Latin script share) across 20+ languages.
O3. Translate any supported language to English with verified output through
    a cascading provider chain (no silent failures).
O4. Extract typed entities (Persons, Organizations, Locations/GPE, Dates,
    Amounts/Money, Jurisdictions, Parties, Legal References, Facilities,
    Events, Groups, Languages, Key topics) with source grounding.
O5. Answer natural-language questions (typed or spoken) strictly from
    retrieved clauses, with citations and relevance scores.
O6. Work fully offline (local Ollama) and fully online (Gemini cloud).
O7. Respond instantly at the UI layer: async jobs + live progress + skeleton
    screens, never a blind spinner or a timeout wall.
O8. Preserve privacy: zero file retention, passwordless auth, no training on
    user data.

6. SYSTEM ARCHITECTURE + DATA FLOW
--------------------------------------------------------------------------------
CLIENT (vanilla JS, no framework)
  upload form / voice note / Q&A box / chatbot / library / compare
        |  POST /api/documents  ->  202 {job_id} (instant)
        |  GET  /api/jobs/<id>  <-  {status, stage, pct, result|error} (poll 2s)
        v
FLASK APP (app.py) — routes, sessions, SQLite, background worker threads
        |
        +-- extract_text()      PDF (pypdf/PyMuPDF) / DOCX (python-docx,
        |                       tables preserved) / TXT / OCR (Tesseract)
        +-- translate_to_english()  [rag.py] language detect -> provider chain
        |     [offline_translator.py] Argos -> Google-batch -> MyMemory(codes)
        |     -> local Ollama (non-fast paths)
        +-- DocumentRAG(text)    chunk (~900 chars/180 overlap) -> TF-IDF +
        |   embeddings -> entity_scan() [spaCy + legal regex + Indian-place
        |   gazetteer + CamelCase/PDF-spacing repair] -> highlight HTML
        +-- _build_entity_result()  audit + buckets + back-translation of
        |   entity labels + markdown report
        +-- answer(question)     hybrid retrieve (70% semantic + 30% lexical,
                                top-4) -> LLM answer with citations, or
                                extractive fallback
        v
PROVIDERS: Gemini 2.5-flash (cloud) | Ollama qwen3:4b local (CPU ~6 tok/s)
           Argos Translate packs (hi/bn/ur->en offline) | Google web MT |
           MyMemory MT | gTTS audio

ASCII flow (upload):
  Browser --file--> /api/documents --> 202 job_id (80 ms measured)
  Worker thread: Reading 8% -> Translating 30% -> Extracting 62% ->
                 Report 85% -> DB save -> Done 100%
  Browser polls /api/jobs, paints skeletons instantly, renders on done.

9. NLP PIPELINE IN DETAIL (METHODOLOGY CHAPTER MATERIAL)
--------------------------------------------------------------------------------
9.1 EXTRACTION. Digital PDFs: pypdf text layer; <80 non-space chars triggers
  Tesseract OCR (scanned PDFs, JPG/PNG/BMP/WEBP). DOCX: body walked in
  order, tables flattened as "cell | cell" rows so parties/fees/dates in
  tables survive. 16 MB cap; extraction runs in its own thread with a
  60 s cap inside background jobs.
9.2 LANGUAGE DETECTION. langdetect first; then dominant-script override:
  if any regional script exceeds 8% of word characters, its language wins
  (fixes English-title confusion; Devanagari checked Marathi-before-Hindi).
9.3 NORMALIZATION. PDF-split Indic glyphs rejoined ("[?] [?]..."), spacing/
  punctuation repaired, CamelCase joins split for display.
9.4 CHUNKING. split_document(): clause-aware split on numbered headings /
  ALL-CAPS headings; else ~900 chars with 180 overlap, sentence-boundary
  preferred. Short agreements keep numbered clauses whole (better cites).
9.5 ENTITY SCAN. spaCy en_core_web_sm over English text + legal regexes
  (money INR/USD/percentages, date ranges, notice periods) + Indian
  state/city gazetteer correcting typical mislabels (Chennai->ORG,
  Tamil Nadu->PERSON) + verb-trim ("founded") + transliteration-consistency
  notes. Output buckets: Persons, Organizations, Locations, Dates,
  Amounts, Jurisdictions, Parties, Legal References, Facilities, Events,
  Groups, Languages, Key topics.
9.6 AUDIT. Local audit: coverage count, low-confidence entities, missing
  expected types, mixed-script (Mumbai/[?]) inconsistencies.
9.7 HIGHLIGHT RENDER. Document re-rendered as HTML with per-label highlight
  colors (PERSON #FFDAB9, ORG #A0E0E0, GPE #FFDC8A, LOC #C1F0C1,
  DATE #A8D8EA, MONEY #FFB6B6, PERCENT #D8BFD8…), used on-screen and in print.
9.8 DISPLAY. Entity values back-translated to the upload language for
  display (Argos for Hindi, chained web translators otherwise); full
  markdown report generated locally (no LLM needed).

10. TRANSLATION SUBSYSTEM
--------------------------------------------------------------------------------
Order per paragraph batch (offline mode):
  1) Argos Translate (true offline; only hi/bn/ur->en packs exist upstream —
     verified via argospm; mr/ta/te/kn/ml/gu/pa have NO upstream pack).
  2) Google web MT in ~2000-char batches + 0.4 s gaps + 12 s hard timeout
     cap (deep_translator issues timeout-less requests; unbounded hangs
     caused the original 40 s client timeouts).
  3) MyMemory with ISO codes FIRST (mr|en verified correct; full names like
     "marathi|english" returned stale fuzzy matches or empty), sentences
     chunked to <=450 chars (free-GET limit), 3 threads, registered email
     (~50k chars/day vs 5k anonymous).
  4) Local Ollama group translation (non-fast paths; qwen3:4b).
Guards: per-backend circuit breakers (trip after 2 consecutive failures,
  120 s cooldown, persistent across requests); request-budget checkpoints
  (_check_deadline between chunks); relaxed verification (>=20 Latin chars)
  plus partial acceptance (English ratio >0.5 AND source-script <0.15).
  Total failure raises an actionable error (wait/retry/Ollama/Gemini key).
Measured: 4-paragraph Marathi doc translates in ~14 s via MyMemory path.

11. RAG QUESTION-ANSWERING DESIGN
--------------------------------------------------------------------------------
Retrieval: hybrid 70% dense-cosine (embeddings: Gemini text-embedding-004
  or Ollama nomic-embed-text) + 30% TF-IDF, top-4 chunks (~900 chars each).
Answering (answer(question, provider)):
  a) LLM path: retrieved [Clause N] excerpts + strict prompt (direct 1-2
     sentence answer FIRST, then ### sections, bullets as
     "- **Entity** — context [Clause N]", no advice). Gemini 2.5-flash when
     key valid; else local Ollama with think:false, keep_alive 30m,
     num_ctx 4096 / num_predict 380 / temp 0.1, anti-ramble stop sequences,
     assistant-prefill ("Based on the document excerpts…"), one retry on
     fast failure. Citations returned with relevance % separately.
  b) Extractive fallback (no LLM reachable): question-word-overlap ranked
     lead sentences + entity bullets — reads as an answer, never a dump.
Chatbot reuses the same endpoint; voice questions via Web Speech API.
Suggestions chips: Persons & Orgs / Locations / Dates / Amounts.

12. AUTHENTICATION & SECURITY
--------------------------------------------------------------------------------
- Passwordless only (users.password_hash is a random value, never used).
- Magic link (primary): single-use sha256-hashed token URL, 15-min expiry,
  older links invalidated on resend; host auto-picked per client —
  localhost for same-machine, server LAN IP (ipconfig address) for phones/
  Wi-Fi devices, APP_BASE_URL override for public deploys.
- OTP alternative: 6-digit code, 10-min expiry, single-use, resend.
- Google OAuth 2.0 (Authlib) with verified-email check; auto-provisioning.
- login_required guard (HTML redirects, JSON 401 for /api/*); per-user
  document isolation in every query; session stores only id+name.
- SMTP via app-password; all secrets in .env (never committed).

  hammering dead backends; requests served while workers run.

  lifts free quota ~10x; Gemini used only when configured.

18. LIMITATIONS (STATE THESE HONESTLY)
--------------------------------------------------------------------------------
L1. English-pivot NER: entities in Tamil/Telugu/etc. are found AFTER
    translation; native-script NER would be more faithful.
L2. en_core_web_sm is small: rare/word-form amounts ("fifty thousand"),
    transliterated names and mixed-script text need the LLM-correction and
    audit passes; some misses remain.
L3. MyMemory MT quality for Marathi-class languages is rough but readable;
    best quality needs Gemini or patient Ollama.
L4. Local 4B model: ~6 tok/s on CPU, occasional rambling (mitigated, not
    eliminated); needs GPU for interactive speed.
L5. OCR = printed text via Tesseract; handwriting and poor scans degrade.
L6. Flask dev server + SQLite: prototype-grade concurrency/durability, not
    production WSGI.
L7. No Argos packs upstream for mr/ta/te/kn/ml/gu/pa (verified) — offline
    MT for these depends on web/local fallbacks.

23. GLOSSARY
--------------------------------------------------------------------------------
NER (Named Entity Recognition): finding + typing spans (person/org/…).
RAG: answering from retrieved passages instead of model memory.
Grounding/citation: every claim points to its source clause.
Pivot translation: non-English -> English before NLP.
spaCy en_core_web_sm: small English CNN NER pipeline used here.
TF-IDF / cosine: lexical retrieval signals blended 30% with 70% dense
  embeddings in retrieve().
Circuit breaker: backend skipped for 120 s after 2 consecutive failures.
Single-flight lock: only one Ollama generation at a time.
Skeleton screen: shimmering placeholder mirroring final layout.
Magic link / OTP: passwordless login via emailed link / 6-digit code.
Zero retention: source files deleted post-extraction.
